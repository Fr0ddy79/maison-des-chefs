## Opportunity #1: Scarcity Signals on /chefs Listing Page

### Problem Statement

The `/chefs` listing page fetches availability data per chef (`{ total, available }` per chefId) but uses it only for binary badge states: `available` (green) / `fully_booked` (gray) / `inquire` (yellow). The homepage creates FOMO with "Available This Weekend," but `/chefs` — the highest-traffic conversion page — shows zero urgency signaling. Visitors browse, compare, and leave without any nudge toward immediate action.

### User Story

**As a** diner browsing `/chefs`
**I want to** see urgency signals on chef availability badges
**So that** I feel compelled to act now rather than continue browsing

**Currently:** A diner sees "Available" on 20 chef cards with no differentiation. No internal pressure to submit an inquiry today.

### Root Cause

The `getBadgeStatus` function in `src/app/chefs/page.tsx` (line 238) computes badge state with only 3 cases:
```typescript
function getBadgeStatus(chefId: string): BadgeType {
  const slot = availability[chefId]
  if (!slot || slot.total === 0) return 'inquire'
  if (slot.available > 0) return 'available'
  return 'fully_booked'
}
```

The `availability` API (`/api/availability`) already returns `{ total, available }` per chef — the scarcity logic is pure client-side computation on existing data.

### Scope

**In:**
- Extend `BadgeType` union to include `'almost_gone' | 'popular'`
- Update `getBadgeStatus()` to compute scarcity tiers:
  - `almost_gone`: `slot.available <= 2` → "Only {N} slots left" (urgency red tint)
  - `popular`: `slot.total >= 5 AND slot.available / slot.total <= 0.2` → "Popular this week" (gold tint)
  - `available`: existing logic (>2 slots, not popular)
- Update `AvailabilityBadge` component styles for new states (same pattern as existing)
- Show slot count in `almost_gone` label: `"Only 2 slots left"`

**Out:**
- Backend changes (data already available)
- Changes to booking flow
- Changes to CTA elements
- Fake scarcity (data-driven only — real slots, real dates)

### Acceptance Criteria

- [ ] `BadgeType` union includes `'almost_gone' | 'popular'`
- [ ] `getBadgeStatus()` computes scarcity from `availability[chefId]` data
- [ ] `almost_gone` badge shows slot count: "Only 2 slots left"
- [ ] `popular` badge shows "Popular this week" label
- [ ] `AvailabilityBadge` renders new styles correctly
- [ ] Build passes with no errors

### Metrics

- **Primary:** `/chefs` → `/book` pageview conversion rate (chefs with `almost_gone` vs. `available` badges)
- **Secondary:** Inquiry submission rate for `almost_gone` chefs
- **Guardrail:** `/chefs` bounce rate (no negative reaction to scarcity signals)

### Open Questions

- Should `almost_gone` badge link directly to booking form on hover? (Would require UX decision)
- Is the `popular` threshold (`total >= 5 AND <=20% remaining`) too aggressive or too conservative for Montreal market?
- Should we limit scarcity badges to chefs with ≥3 bookings to avoid labeling new chefs?
