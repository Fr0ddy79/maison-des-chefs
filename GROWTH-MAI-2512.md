## Executive Summary

Fixed a stale hardcoded social proof number and made the waitlist count dynamic. The landing page was displaying "Join 47+ food lovers already waiting" with a static number — disconnected from the actual `emails` table count. Now the StatsBar pulls real waitlist data from the database and surfaces it alongside chef/booking stats.

---

## What Was Changed

### 1. `/api/stats` — Added `waitlist_count` to the stats endpoint

The `GET /api/stats` endpoint now counts rows in the `emails` table:

```ts
// Count email waitlist signups
const { count: waitlistCount, error: waitlistError } = await supabase
  .from('emails')
  .select('*', { count: 'exact', head: true })
```

Returns:
```json
{
  "chefs_available": 5,
  "dinners_booked": 2,
  "waitlist_count": 47
}
```

### 2. `StatsBar.tsx` — Surfaced waitlist count as a third stat

Added `waitlist_count` to the `Stats` type and renders it as a third social proof line:

```
[5] Verified Chefs Available  [2] Dinners Booked  [47+] Food Lovers Waiting
```

- Hidden on small (`sm`) viewports — chefs and dinners Booked take priority on mobile
- Only shown when `waitlist_count > 0`
- Pluses on the number (e.g., `47+`) to match the previous display convention

### 3. `page.tsx` — Removed hardcoded "47+" copy

Replaced the static copy line under the waitlist form:

| Before | After |
|--------|-------|
| "Join 47+ food lovers already waiting" | "Join our community of food lovers for exclusive updates" |

**Rationale:** The copy no longer needs to repeat the number (it's now in StatsBar above), and "47+" was stale regardless — the number changes with every signup. Generic copy avoids the need to keep it in sync.
